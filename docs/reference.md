# Справочник панели

Панель управления клиентскими конфигурациями AmneziaWG 3.0 и 3.1.

Один процесс обслуживает несколько интерфейсов AWG сразу. Для каждого он
читает серверный конфиг, правит **только** секции `[Peer]`, применяет
изменения через `awg syncconf` и собирает клиентский `.conf` с QR-кодом
заново при каждой выдаче. Секция `[Interface]` копируется побайтово: кода,
способного её изменить, в проекте не существует.

Одна страница за HTTP Basic auth, переключение между интерфейсами прямо в
браузере. Слушает адрес **внутри самого туннеля** — снаружи панели не
существует.

```
пир в браузере ──► [Peer] в awg3.conf ──► awg syncconf ──► проверка постусловия
                        ▲                                        │
                        └──────────── откат при расхождении ◄─────┘
```

## Что делает и чего не делает

**Умеет:**

- обслуживать несколько интерфейсов AWG одним процессом, с переключателем в
  вебе — см. [Несколько интерфейсов](#несколько-интерфейсов);
- показывать список пиров с живым статусом: адрес, последний handshake, rx/tx;
- добавлять пира по имени — генерация ключей и PSK, выбор свободного адреса,
  применение и выдача клиентского `.conf` вместе с QR-кодом;
- править уже выпущенного пира: имя, адрес в туннеле, DNS, маршруты,
  keepalive, MTU, endpoint, джиттер и произвольные дополнительные поля — см.
  [Правка параметров пира](#правка-параметров-пира);
- менять ключи пира, не теряя его идентификатор, имя и адрес — см.
  [Ротация ключей](#ротация-ключей);
- править умолчания интерфейса прямо из веба, без рестарта сервиса — см.
  [Умолчания интерфейса](#умолчания-интерфейса);
- удалять и временно отключать пира с возможностью включить обратно;
- выдавать ранее созданный конфиг повторно — он всегда собирается заново по
  текущим данным, а не читается с диска.

**Сознательно не умеет:**

- **править серверный `[Interface]` ни одного из интерфейсов.** Обфускация
  (`S1..S4`, `H1..H4`, `HeaderProtectionKey`, `ContentPaddingAddition`),
  `ListenPort`, `MTU` сервера, `PostUp`/`PostDown` — панель их не трогает и не
  может тронуть по построению, см.
  [Безопасность мутаций](#безопасность-мутаций). Такие правки делаются руками
  по SSH;
- управлять systemd-юнитом интерфейса, его портом на файрволе, правилами NAT;
- устанавливать и обновлять сам AmneziaWG;
- работать с другими протоколами и с маршрутизацией;
- вести историю трафика, лимиты и квоты;
- разграничивать пользователей — доступ единый, по одному Basic-логину на все
  интерфейсы сразу.

**`awg setconf` не вызывается никогда и ниоткуда.** Интерфейс `runtime.Runner`
(`internal/runtime/runner.go`) физически не содержит такого метода: есть
`Show`, `ShowConf`, `Strip`, `SyncConf`, `GenKey`, `GenPSK`, `PubKey`, и только
`SyncConf` трогает живое устройство. Причина не в стиле, а в измеренном факте:
`awg setconf` рвёт уже установленные сессии, `awg syncconf` — нет; это
проверено на живом сервере при разработке инварианта применения (раздел 6.1
спеки). Вся запись на устройство идёт только через `syncconf` поверх
результата `awg-quick strip`.

## Две сборки

Бинарь собирается в двух вариантах через build-тег `readonly`:

| | Полная | `readonly` |
|---|---|---|
| Команда | `make build` | `make build-readonly` |
| Файл | `dist/awg3panel` | `dist/awg3panel-readonly` |
| Список пиров, живой статус | есть | есть |
| Добавление/удаление/отключение пира, CLI `add`/`rm`/`disable`/`enable` | есть | **нет** |
| Заявки на подключение/отвязку интерфейса, CLI `iface`, вкладка «Интерфейсы» | есть | **нет** |

В `readonly`-сборке обработчиков мутаций нет физически, а не выключены флагом:
файлы `cmd/awg3panel/cli.go`, `internal/web/handlers_mutate.go`,
`cmd/awg3panel/server_full.go` несут тег `!readonly` и в такой сборке не
компилируются вовсе. Это осознанная этапность выката (раздел 12.1 спеки):
первая версия на боевом сервере физически не могла ничего испортить, потому
что писать было нечем. Какая сборка перед вами — видно из версии:

```
$ awg3panel version
awg3panel <версия> (сборка: полная)
$ awg3panel-readonly version
awg3panel <версия> (сборка: только чтение)
```

## Установка

Сборка — на рабочей машине, кросс-компиляция в статический бинарь, безразличный
к glibc целевой системы. На сервере не нужны ни Go, ни исходники:

```bash
make build            # dist/awg3panel — полная сборка
make build-readonly    # dist/awg3panel-readonly — только чтение
```

Копирование и установка:

```bash
scp dist/awg3panel deploy/install.sh deploy/awg3panel.service deploy/config.example.yaml \
    root@сервер:/root/awg3panel-deploy/
ssh root@сервер
cd /root/awg3panel-deploy
./install.sh --dry-run     # что будет сделано, ничего не пишет на диск
./install.sh                # собственно установка
```

`install.sh` идемпотентен: повторный запуск на настроенной системе не меняет
состояние (бинарь и юнит перезаписываются только при реальном изменении;
существующий `config.yaml` никогда не перетирается). Первый запуск создаёт
каталоги, кладёт бинарь и `config.yaml` из примера, ставит юнит — но **не
запускает сервис**, пока в `config.yaml` не задан bcrypt-хеш пароля (метка
`ЗАМЕНИТЬ`). Хеш получается паролем через pipe, а не аргументом: аргумент
командной строки оседает в истории оболочки, стандартный ввод — нет.

```bash
printf '%s' 'ваш-пароль' | /usr/local/bin/awg3panel hash-password
```

Полученную строку `$2a$12$...` — в `auth.bcrypt` в `/etc/awg3panel/config.yaml`,
остальные поля сверить с таблицей ниже, и запустить установку ещё раз — теперь
она включит и запустит сервис:

```bash
./install.sh
systemctl status awg3panel
```

Откат:

```bash
systemctl disable --now awg3panel
rm -rf /usr/local/bin/awg3panel /etc/awg3panel /var/lib/awg3panel \
       /etc/systemd/system/awg3panel.service
```

Серверный `awg3.conf` при этом не трогается — состав пиров, выпущенных
панелью, остаётся как есть.

## Конфигурация

`/etc/awg3panel/config.yaml`, права `0600`. Загрузка строгая: невалидный
конфиг — отказ старта с внятной ошибкой, а не работа на умолчаниях.

Верхний уровень:

| Поле | Значение | Пример |
|---|---|---|
| `listen` | адрес:порт панели. Обязан быть конкретным адресом **внутри туннеля** — `0.0.0.0`, `::` и пустой хост валидация отвергает | `10.11.0.1:8081` |
| `auth.user` | имя пользователя Basic auth, общий на все интерфейсы | `admin` |
| `auth.bcrypt` | bcrypt-хеш пароля, получить через `awg3panel hash-password` | `$2a$12$...` |
| `interfaces` | список управляемых интерфейсов AWG, см. ниже | — |

Каждый элемент `interfaces`:

| Поле | Значение | Пример |
|---|---|---|
| `id` | slug интерфейса: `[a-z0-9-]{1,32}`, уникален. Часть URL в вебе и значение флага `--iface` | `awg31` |
| `title` | подпись вкладки в вебе; не задано — подставляется `id` | `awg3.1` |
| `interface` | имя устройства для `awg show`/`awg syncconf`, уникально | `awg3.1` |
| `config` | путь к серверному конфигу этого интерфейса | `/etc/amnezia/amneziawg/awg3.1.conf` |
| `bin_dir` | каталог с бинарями `awg`, `awg-quick` и `amneziawg-go` для этого интерфейса; без `amneziawg-go` сводка на весь срок жизни процесса остаётся без поля `version` (см. «Сводка по интерфейсу и генераторы параметров») | `/opt/awg3.1/bin` |
| `interface_edit` | зарезервировано под будущую правку серверного `[Interface]`; в этой версии панели ни на что не влияет — такого кода в бинаре нет (см. «Что делает и чего не делает») | `false` |
| `client.*` | **сид** умолчаний клиента: `endpoint`, `allowed_ips`, `persistent_keepalive`, `dns`, `jc`/`jmin`/`jmax`. Используется только при первом запуске интерфейса — переносится в `defaults.json` и дальше не перечитывается (см. «Умолчания интерфейса») | `endpoint: "203.0.113.10:51772"` |
| `storage.state` | путь к `peers.json` этого интерфейса | `/var/lib/awg3panel/awg31/peers.json` |
| `storage.backups` | каталог бэкапов серверного конфига этого интерфейса | `/var/lib/awg3panel/awg31/backups` |
| `storage.keys` | каталог приватных ключей клиентов этого интерфейса (`0700`, файлы `0600`) | `/var/lib/awg3panel/awg31/keys` |
| `storage.client_configs` | легаси: каталог, куда старая (одноинтерфейсная) версия панели складывала выданные `.conf`. Нужен только на время миграции приватных ключей оттуда в `storage.keys` (см. «Миграция ключей со старой установки»); когда каталог опустеет — поле можно убрать | `/var/lib/awg3panel/clients` |

Пути `config`, `storage.state`, `storage.backups`, `storage.keys` не должны
повторяться между интерфейсами: общий файл означал бы, что согласование
состояния одного интерфейса вычищает пиров другого. Панель проверяет это при
старте и отказывается запускаться при пересечении.

`defaults.json` (а в будущем — и `pending-interface.json`) собственных полей в
`config.yaml` не имеет: он всегда лежит рядом с `peers.json`, в том же каталоге.

Старый одноинтерфейсный формат конфига (секции `awg:`, `client:`, `storage:`
прямо на верхнем уровне, без `interfaces:`) по-прежнему читается и на лету
сворачивается в список из одного интерфейса с `id: default`. Присутствие
одновременно старых секций и `interfaces:` — ошибка старта, а не приоритет одной
формы над другой: если в файле есть обе, панели неоткуда знать, какая из них
действует, и молчаливый выбор был бы правильным только в половине случаев.

`[Interface]` клиентского конфига (обфускация: `S1..S4`, `H1..H4`,
`HeaderProtectionKey`, `ContentPaddingAddition`, `MTU`) в `config.yaml` не
хранится — панель копирует его из живого `[Interface]` сервера при каждой
выдаче, поэтому смена обфускации на сервере автоматически отражается в новых
конфигах.

### Поля AmneziaWG 3.1

`RandomTrailers` и `DisableCookies` необязательны: сервер без них ведёт себя
ровно как 3.0. Панель обращается с ними иначе, чем с полями списка выше, и
разница видна снаружи в двух местах.

**`ContentPaddingAddition` перестаёт быть обязательным, когда `RandomTrailers`
включён.** На транспорте второй перебивает первый, поэтому вместе они не
задаются, и сервер 3.1 с включёнными хвостами намеренно не несёт
`ContentPaddingAddition` — требовать его значило бы объявить исправный сервер
сломанным. Послабление узкое: `RandomTrailers = off` его **не** включает —
такой сервер это обычный 3.0, и без `ContentPaddingAddition` клиент к нему
молча не подключится.

**Клиенту переносится только включённое значение.** `RandomTrailers`
двусторонний: сервер с ним дописывает случайные хвосты, и клиент без этой же
строки их не разберёт — поэтому включённое поле обязано доехать до выданного
`.conf`. Выключенное, наоборот, в файл не попадает: бинарь 3.1 печатает эти
поля в `awg showconf` всегда, в том числе как `off`, а строка
`RandomTrailers = off` в клиентском конфиге смысла не несёт (это и есть
поведение по умолчанию) и при этом ломает разбор у клиентов версии 3.0.

⚠️ **Отдельно от панели:** если бинарь на сервере поднят до 3.1, устройство
начинает печатать эти поля в `awg showconf`, даже когда они выключены. Файл
конфига при этом не меняется, и возникает расхождение «на устройстве есть, в
файле нет» — а `syncconf` сбрасывает всё, чего нет в применяемом файле. Страж
расхождения на таком сервере откажет в любой мутации, пока в `[Interface]`
файла не появятся строки ровно в том виде, в каком их печатает `awg showconf`:

```
RandomTrailers = off
DisableCookies = off
```

Это правка серверного конфига, а не панели: сама она `[Interface]` не трогает
и починить это за оператора не может.

### Тайминги и джиттер

Кроме обфускации панель переносит клиенту **рандомизированные тайминги**
сервера — `RekeyAfterTime`, `RekeyTimeout`, `RejectAfterTime`,
`KeepaliveTimeout`, `MaxHandshakeAttempts`. Это третий механизм AWG 3.0 наряду
с header protection и content padding, и это параметры протокола, а не
украшение серверного файла: сервер с `RejectAfterTime = 165-195` ведёт сессию
иначе, чем клиент с дефолтными 180.

Переносятся только заданные на сервере. Если сервер их не задаёт, он работает
на дефолтах протокола — и клиент обязан остаться на тех же, поэтому выдумывать
значения панель не станет.

**Джиттер (`Jc`/`Jmin`/`Jmax`) задаётся умолчаниями интерфейса**, а не читается
с сервера: это чисто клиентский механизм. `Jc` пакетов со случайными данными
размером `Jmin`..`Jmax` байт уходят ПЕРЕД рукопожатием и размывают его
временной и размерный профиль — без них первый пакет несёт узнаваемый профиль
WireGuard. Сервер junk-пакеты просто отбрасывает, согласовывать значения не
требуется. Тройка задаётся либо целиком, либо не задаётся вовсе (`0/0/0` =
джиттер выключен); `Jmin` обязан быть строго меньше `Jmax`.

Менять после первого запуска — через вкладку «Настройки по умолчанию», а не правкой
`config.yaml`: тот является лишь сидом при первом запуске интерфейса.

## Несколько интерфейсов

Один процесс `awg3panel` обслуживает весь список `interfaces` из `config.yaml`
одновременно. Каждый интерфейс полностью независим: свой серверный конфиг, свой
`bin_dir`, свои `peers.json`/`defaults.json`/бэкапы/ключи — правка одного не
может задеть другой ни при каких обстоятельствах, потому что общих файлов между
ними нет и быть не может (см. таблицу выше).

В вебе интерфейсы — это переключатель вкладок в шапке страницы; выбранная
вкладка запоминается в адресной строке, так что на конкретный интерфейс можно
сохранить прямую ссылку. `GET /api/ifaces` отдаёт список интерфейсов с их `id`,
`title`, именем устройства и флагом `interface_edit` — панель показывает вкладку
для каждого элемента этого списка независимо от его настроек.

В CLI интерфейс выбирается флагом `-iface <id>`; без флага команды работают с
первым интерфейсом по порядку в `config.yaml`. Команда `awg3panel ifaces`
печатает список всех интерфейсов — то же самое, что отдаёт `GET /api/ifaces`, но
текстом в терминал:

```
$ awg3panel ifaces
awg3     awg3 (боевой)   устройство awg3      правка [Interface]: нет
awg31    awg3.1          устройство awg3.1    правка [Interface]: нет
```

Значение `interface_edit` из конфига в эту строку тоже попадает, но ни на что не
влияет: кода, который читал бы его для решения «пускать правку или нет», в этой
версии панели не существует — фаза 2 спеки 3.1 (правка `[Interface]` под safe
mode) не реализована, см. `CLAUDE.md`.

## Подключение и отвязка интерфейса

Список `interfaces` в `config.yaml` можно расширять и сужать не только
правкой файла руками, но и из панели — двумя операциями, ни одна из которых
не трогает сам туннель:

- **подключение (`attach`)** — берёт под управление интерфейс, уже поднятый
  на хосте (устройство существует, `.conf` лежит на диске), вписывает его
  блок в `config.yaml` и заводит для него каталог состояния. Панель, у
  которой этого интерфейса не было ни разу, начинает показывать его пиров;
- **отвязка (`detach`)** — вырезает блок интерфейса из `config.yaml` обратно.
  На хосте не меняется **ничего**: устройство продолжает работать, `.conf`
  остаётся на месте, клиенты остаются подключены. Каталог состояния с
  приватными ключами выданных пиров тоже остаётся на диске — отвязка не
  уничтожает и не отправляет в архив ничего.

**Повторно подключить тот же `id` эта версия не умеет.** Подключение
отказывает, если каталог состояния `/var/lib/awg3panel/<id>/` существует и
не пуст, — а после отвязки он именно такой. Спека 2026-08-25 (раздел 7)
описывает намеренное исключение для этого случая, но в коде его нет:
`PlanAttach` отказывает безусловно. Практически это значит, что отвязка
обратима только через `rm -rf /var/lib/awg3panel/<id>` руками, то есть ценой
приватных ключей всех выданных с этого интерфейса пиров — ради обхода
которой отвязка и заведена. Каталог удаляется **осознанно и вручную**;
подключить интерфейс под ДРУГИМ `id` (у него свой, пустой каталог) можно и
сейчас, но выданные раньше конфиги при этом всё равно не подхватятся.

Это признанный долг, а не забытая мелочь: проверка, описанная спекой,
опирается на сверку публичного ключа сервера с тем, для которого выписаны
пиры, а `store.State` публичного ключа сервера не хранит вовсе — сверку
придётся строить иначе, и это работа плана Б (см. `STATUS.md`).

Файл `.conf` при обоих действиях **только читается** — незыблемое правило 2
этого репозитория не задето даже формально: кода, способного записать
`[Interface]`, в `internal/iface` нет так же, как и во всём остальном
бинаре.

**Схема применения — заявка, а не немедленное действие.** Панель (демон,
запертый песочницей systemd) не пишет `config.yaml` и не перезапускает себя
сама. Нажатие «Подключить»/«Отвязать» во вкладке «Интерфейсы» только
записывает **заявку** — JSON-файл в `/var/lib/awg3panel/requests/`,
описывающий будущее изменение хоста. Применяет её отдельная команда,
которую оператор запускает по SSH под root, вне песочницы демона:

```bash
ssh root@сервер
awg3panel iface requests        # что лежит в очереди — прочитать перед apply
awg3panel iface apply           # применить по одной, с подтверждением каждой
awg3panel iface apply --dry-run # то же самое, но ничего не пишет на диск
awg3panel iface cancel <имя>    # снять заявку, не применяя (имя — из iface requests)
```

`iface apply` без `--dry-run` требует интерактивного терминала: если ввод —
не терминал, команда отказывает явной ошибкой, а не тихо считает пустой
ввод согласием. На каждую заявку `apply` печатает то же самое описание, что
показывала консоль перед записью (устройство, конфиг, каталог состояния,
для `detach` — число пиров **по `.conf` на момент сборки заявки**, не по
живому серверу), и спрашивает набрать `attach` или `detach` для
подтверждения; пустой ввод — заявка пропускается, а не отклоняется, и
остаётся в очереди на следующий запуск.

Порядок шагов внутри `apply` — снимок `config.yaml` → бэкап → правка текста
→ (для `attach`: каталог состояния) → `systemctl restart awg3panel` →
проверка постусловия (демон активен, заявленный `id` появился/исчез из
`config.yaml`, для `attach` — устройство отвечает на `awg show`). Любой
сбой откатывает `config.yaml` к бэкапу и перезапускает панель заново —
оператор не должен остаться без консоли из-за неудавшейся заявки.

**Почему порядок работ на боевом хосте начинается не с панели.** Отвязка
отказывает, если интерфейс несёт адрес, на котором слушает сама панель, —
отвязать его через `iface apply` нельзя (удаления интерфейса в этой версии
нет вовсе, см. «Чего в этой версии нет» ниже; когда его добавит план Б, оно
унаследует тот же отказ по той же причине). Это не тонкость реализации, а
защита от самострела: на обоих боевых хостах `listen` панели указывает
внутрь `awg3` (`10.x.0.1:8081`), и через тот же интерфейс идёт SSH —
рестарт после такой отвязки оставил бы панель без адреса, на котором ей
есть что слушать, а до хоста было бы не достучаться (прямого SSH из РФ нет,
только туннель через тот же `awg3`). Поэтому замена `awg3` на новый туннель
**не может начаться с его отвязки**: сначала поднимается и заводится под
управление новый интерфейс, на него переводятся пиры (включая тот, через
который идёт SSH), меняются `listen` панели и адрес обратного прокси перед
ней — и только после этого старый интерфейс можно отвязать. Два шага из
трёх здесь — эксплуатация, а не код: `iface apply` их не выполняет и не
проверяет, он проверяет только собственный, последний шаг.

**Чего в этой версии нет.** Заведение **нового** интерфейса «с нуля»
(генерация ключей, подсети, конфига и systemd-юнита) и удаление интерфейса
с архивом каталога состояния — план Б поверх этого фундамента, он ещё не
написан. Искать в коде мастер создания или архивное удаление бессмысленно,
это ожидаемо — см. `CLAUDE.md`.

## CLI

Панель — основной интерфейс; CLI-мутации — инструмент восстановления на
случай, когда демон (`awg3panel serve`) не работает. Обе формы идут через
один и тот же `issuer.Service` и один и тот же инвариант применения
(см. ниже) — разница только в способе вызова. Правка параметров пира и
ротация ключей через CLI сознательно не выведены: второй вход к тем же
мутациям — лишняя поверхность, пока панель работает и веб-путь доступен.

```
awg3panel [-config путь] [-iface id] serve       запуск HTTP-сервера (по умолчанию); -iface не влияет — сервер обслуживает все интерфейсы сразу
awg3panel [-config путь] [-iface id] list        список пиров, состояние, последний handshake
awg3panel [-config путь] [-iface id] add <имя>   выпустить пира, напечатать клиентский конфиг в stdout
awg3panel [-config путь] [-iface id] rm <id>     удалить пира
awg3panel [-config путь] [-iface id] disable <id> временно отключить пира
awg3panel [-config путь] [-iface id] enable <id> включить обратно ранее отключённого
awg3panel [-config путь] ifaces                  список интерфейсов: id, заголовок, устройство, разрешена ли правка [Interface]
awg3panel [-config путь] iface requests|apply|cancel  исполнитель заявок на подключение/отвязку интерфейса — см. «Подключение и отвязка интерфейса»
awg3panel hash-password                          bcrypt-хеш пароля (аргументом или из stdin)
awg3panel version                                версия и тип сборки
```

`-config` по умолчанию — `/etc/awg3panel/config.yaml`. `-iface` выбирает
интерфейс для `list`/`add`/`rm`/`disable`/`enable` по его `id` из
`config.yaml`; без флага берётся первый интерфейс по порядку в файле,
неизвестный `id` — отказ со списком доступных. `ifaces` работает без `-iface`
(печатает их все сразу) и одинаково в обеих сборках — в отличие от мутирующих
команд, ей нечего ограничивать. `iface` тоже не подчиняется `-iface` и по той
же причине: она про набор интерфейсов целиком, а не про один уже
сконфигурированный. В `readonly`-сборке доступны только `list` и `ifaces`;
`add`/`rm`/`disable`/`enable` и `iface` отвечают «команда недоступна: бинарь
собран в режиме только чтения» — отдельно от «неизвестная команда», чтобы
опечатка не выглядела осознанным ограничением.

Перед мутацией CLI проверяет, слушает ли уже кто-то `listen`-адрес из своего
же конфига, и если да — отказывает с кодом 4:

```
$ awg3panel add тест
похоже, панель уже запущена и слушает 10.11.0.1:8081 — измените пира через
веб-интерфейс, либо сначала остановите демон и повторите команду
```

Это **совет, а не гарантия взаимного исключения**: однократный TCP-опрос
адреса без блокировки и без рукопожатия с демоном. Между опросом и
применением остаётся окно, а проверяется `cfg.Listen` из **своего** `-config`,
а не то, что реально слушает работающий демон — если конфиги разошлись (демон
не перечитал изменившийся `listen:`, либо CLI вызван с другим `-config`),
проверка тихо промолчит и мутация выполнится параллельно с демоном. Файловой
блокировки между процессами в коде нет — решение сознательно отложено.

### Коды возврата

| Код | Значение |
|---|---|
| `0` | успех |
| `1` | внутренняя ошибка (в том числе — не загрузился конфиг) |
| `2` | некорректный ввод: пустое имя/id, недостающий аргумент, пустой пароль в `hash-password` |
| `3` | пир с таким id не найден |
| `4` | похоже, панель уже запущена и слушает тот же адрес |

Коды классифицируются по типу ошибки (`errors.Is`), а не по номеру команды —
скрипт вокруг CLI различает ситуации, не разбирая текст на stderr.

## Безопасность мутаций

Любая мутация, которая доходит до серверного конфига (`add`/`rm`/`disable`/
`enable`, правка имени или адреса пира, ротация ключей — из панели или из
CLI, где применимо), проходит одну и ту же последовательность
(`internal/issuer/apply.go`, раздел 6 спеки):

1. **снимок ДО** — `awg show <iface> dump` и `awg showconf <iface>`;
2. предварительная сверка: `[Interface]` файла на диске обязан совпадать со
   снимком устройства, иначе применение отменяется ещё до записи;
3. **изменение текста** — хирургически, ровно один блок `[Peer]` дописывается
   или вырезается; `[Interface]` и чужие блоки `[Peer]` задеть нельзя — в
   коде нет пути, которым это было бы возможно;
4. **бэкап** в `/var/lib/awg3panel/backups`, права `0600`, хранятся последние
   20, старые удаляются автоматически. Отдельно, в начале каждой мутации (выпуск,
   отключение, включение, удаление, правка, ротация ключа, правка умолчаний),
   снимается **состояние интерфейса** — `peers.json`, `defaults.json` и ключи
   клиентов — в `<storage.backups>/state/state.<UTC>-<n>.tar.gz` (0600, последние
   20). Отказ снимка отменяет мутацию. Восстановление: остановить панель,
   `tar -xzf <снимок> -C <каталог storage.state>` (ключи лягут в `keys/` — если
   `storage.keys` указывает в другое место, перенести их туда), запустить панель;
5. **атомарная запись** — временный файл рядом, `chmod 0600`, `rename`;
6. **`awg syncconf`** через результат `awg-quick strip`, переданный временным
   файлом — не аргументом и не подстановкой процесса, ключи не должны
   попадать ни в `/proc`, ни в общий `/tmp`;
7. **проверка постусловия** — сверка со снимком ДО: прежние пиры на месте,
   их `AllowedIPs` и `PresharedKey` не изменились, `latest handshake` не
   обнулился, device-параметры `[Interface]` идентичны, ожидаемое изменение
   произошло;
8. **откат при любом расхождении** — файл восстанавливается из памяти,
   `syncconf` повторяется, устройство сверяется со снимком ДО ещё раз; если
   откат не восстановил рабочее состояние, ошибка так и называется — «откат
   не удался», а не «изменения откачены».

Приватные ключи и PSK не попадают ни в логи, ни в тексты ошибок, ни в
HTTP-ответы 5xx — фильтруется даже сырой `stderr` внешних команд, поскольку
сам бинарь `awg` способен вернуть секрет в тексте своей ошибки.

Правка пира и ротация ключей проходят тот же инвариант, только шаг 3 (изменение
текста) у них разный: переименование и смена адреса заменяют существующий блок
`[Peer]` на месте, ротация убирает старый блок и дописывает новый на
освободившееся место — публичный ключ на устройстве это идентичность пира, и
смена ключа для инварианта равносильна замене одного пира другим, а не правке
существующего. Правка одних только клиентских оверрайдов (маршруты, DNS,
keepalive, MTU, endpoint, джиттер, `extra`) серверный конфиг не трогает
вовсе — блок `[Peer]` эти поля не хранит, менять там нечего. Мутация без
единого действительного изменения (например, `PATCH` с теми же именем и
адресом и без оверрайдов) возвращается до бэкапа и `syncconf` — риск на живом
устройстве не оправдан нулевым результатом.

## Имена пиров и подтверждение необратимых действий

**Имя пира берётся из комментария внутри его блока `[Peer]`.** Панель пишет
такой комментарий сама, когда выпускает пира (`# awg3panel: Алёша`), но
читает **любой** — в том числе оставленный человеком задолго до её установки:

```ini
[Peer]
# роутер дома
PublicKey = …
AllowedIPs = 10.11.0.2/32
```

Такой пир появится в списке как «роутер дома». Пир вообще без комментария
получает имя `peer-<12 hex>` — его всегда можно переименовать в консоли,
и переименование комментарий в конфиге не перебивает: имя, выбранное
человеком через панель, старше того, что написано в файле.

Два правила отбора, оба продиктованы тем, что имя обязано быть принято
панелью обратно при правке:

| Комментарий | Имя |
|---|---|
| длиной до 40 символов | берётся целиком |
| длиннее 40 символов, вида «название — пояснение» | берётся голова до тире с пробелами |
| длиннее 40 символов без разделителя, либо со скобками `[` `]` | не берётся, остаётся `peer-<hex>` |

**Удаление пира и ротация его ключей подтверждаются вводом имени.** Промах
при наборе не молчалив: панель говорит, что имя не совпало и что ничего не
сделано. Отказ (Esc или «Отмена») молчалив намеренно — человек передумал,
сообщать ему об этом нечего. Пробелы по краям введённого срезаются: имя в
`peers.json` уже обрезано, а пробел, прилипший при копировании из таблицы, —
самый вероятный источник промаха.

## Правка параметров пира

В разделе **Подключения** нажмите **Настроить** в нужной строке. Кнопка
**Открыть** показывает состояние связи, QR-код и ссылки на клиентский конфиг.

У уже выпущенного пира редактируются: имя, адрес в туннеле и клиентские
параметры — DNS, что маршрутизировать в туннель, `PersistentKeepalive`, `MTU`,
`Endpoint`, джиттер `Jc`/`Jmin`/`Jmax` и произвольные дополнительные
client-side поля (`extra`) — то, что панель не знает по имени, но что нужно
для AWG 3.1 и будущих версий протокола.

**Два разных `AllowedIPs` — не опечатка, а два разных смысла одного и того же
имени поля:**

- **адрес в туннеле** — это `AllowedIPs` серверного блока `[Peer]`: единственный
  `/32`-адрес, по которому сервер узнаёт пакеты этого клиента. Смена этого поля —
  правка самого серверного конфига через тот же инвариант применения, что и у
  add/remove/disable (см. «Безопасность мутаций»); сессия у этого пира
  переустанавливается, у всех остальных — нет;
- **маршрутизировать в туннель** — это `AllowedIPs` **клиентского** конфига: что
  клиент отправляет через туннель, а что — напрямую (`0.0.0.0/0` — всё, более
  узкий список — только перечисленные сети). Это персональный оверрайд пира или
  умолчание интерфейса; серверного конфига оно не касается вовсе — поля для
  клиентских маршрутов в `[Peer]` попросту нет.

Спутать их — дорогая ошибка: правка не того поля либо не выпустит клиента дальше
одного адреса, либо не изменит то, что реально уходит в туннель.

Персональные значения хранятся как `overrides` в `peers.json`: отсутствие поля
означает «наследовать умолчание интерфейса», явное значение — «использовать
именно его», а явно пустая строка (там, где это осмысленно, например `dns: ""`)
— «этому пиру не нужно то, что есть в умолчаниях». Сбросить оверрайд назад в
наследование можно, отправив `null` — панель различает эти три состояния на
всём пути от формы до диска.

Валидация `extra` жёсткая, потому что содержимое печатается прямо в файл
клиентского конфига: имя поля — буква и до 15 букв/цифр, значение — без
переводов строк, скобок и пробелов по краям, а поле, у которого уже есть
отдельное место (`DNS`, `MTU`, `Jc`, ...), через `extra` не задать — иначе в
файле оказались бы две строки одного ключа с неопределённым приоритетом у
клиента.

## Ротация ключей

Действие «Ротировать ключи» выдаёт пиру новую пару ключей и новый
`PresharedKey`, сохраняя его `id`, имя и адрес — ссылки на пира и файл с его
приватным ключом (`keys/<id>.key`) остаются на том же месте. На сервере это не
правка пира, а замена одного другим: старый публичный ключ уходит из
серверного конфига, новый добавляется на то же место.

**Старый клиентский конфиг перестаёт работать немедленно** — сервер его больше
не узнаёт. Ротацию стоит делать, только когда новый конфиг (или QR) можно сразу
же передать владельцу устройства; панель возвращает его в том же ответе, что и
при первой выдаче.

Ротация — единственный способ вернуть в строй пира без известного приватного
ключа (заведённого вручную до установки панели либо с неудавшейся миграцией,
см. «Миграция ключей со старой установки»): после неё ключ панели известен, и
обычная выдача конфига начинает работать.

Если состояние `peers.json` разошлось с сервером (например, предыдущая ротация
успела заменить ключ на устройстве, но не успела записать это в `peers.json`),
повторная ротация отказывает явной ошибкой (HTTP 409) вместо того, чтобы молча
выпустить третий ключ или потерять метаданные пира. Специально открывать список
пиров ради починки не нужно и не стоит: расхождение согласуется само собой при
ближайшем обновлении списка (страница и так опрашивает его каждые 10 секунд) —
но при этом согласовании пир теряет `id`, дату выпуска и персональные
оверрайды: механизм самолечения не различает «пира убрали руками мимо панели» и
«прошлая ротация не дописалась», и в обоих случаях заводит запись заново, как
будто увидел пира впервые. Согласование, которое не выбрасывало бы запись, —
структурная починка, в этой версии панели её нет.

## Умолчания интерфейса

Редактируемые умолчания клиента (`endpoint`, маршруты, keepalive, DNS,
джиттер, `extra`) живут в `defaults.json` рядом с `peers.json` соответствующего
интерфейса, а не в `config.yaml`. Причина разделения: `config.yaml` — файл
развёртывания, его кладёт `install.sh`, лежит он в `/etc` с правами `600` и
содержит хеш пароля — переписывать его из сервиса значило бы терять комментарии
YAML при каждой правке и конфликтовать с идемпотентностью установщика.

`config.yaml` при этом остаётся **сидом**: секция `client` интерфейса
переносится в `defaults.json` при первом запуске и с этого момента больше не
перечитывается — правка `client.*` в уже работающей установке ничего не
меняет. Панель фиксирует это в журнале один раз за время работы процесса на
этот интерфейс, при первом реальном обращении к его умолчаниям — не при
старте: `defaults.json` читается лениво, из выпуска пира, ротации, сборки
конфига или самой вкладки «Настройки по умолчанию», смотря что случится раньше. Дальше
умолчания правятся вкладкой «Настройки по умолчанию» в вебе, без рестарта сервиса; они
применяются ко всем пирам, у которых по конкретному полю нет персонального
оверрайда.

Смена умолчаний, как и правка оверрайдов пира, серверного конфига не
касается — она видна в конфигах, которые клиенты получат при следующей выдаче.

## Сводка по интерфейсу и генераторы параметров

Консоль показывает не только список пиров, но и состояние самого интерфейса —
`GET /api/ifaces/{iface}/summary`: порт, MTU, публичный ключ, версия бинаря,
счётчики пиров (всего / активны / нет связи дольше суток / никогда не
подключались) и суммарные RX/TX с указанием, чей был последний хендшейк.
Маршрут доступен в обеих сборках — это чтение, как и список пиров; пороги
«активен» (хендшейк не старше 180 секунд) и «нет связи» (старше 24 часов) —
константы пакета `issuer`, а не настройки.

Сводка и список пиров — два независимых read-маршрута: каждый сам выполняет
`awg show <iface> dump` и разбирает его заново. Консоль опрашивает оба
каждые 10 секунд, поэтому на каждый опрос приходится на один exec больше,
чем было бы при общем кэше (12 в минуту вместо 6) — это принято сознательно:
связать два независимых маршрута общим кэшем ради экономии одного дешёвого
exec значило бы завязать их друг на друга, а такая связь дороже лишнего
вызова `awg show`. Единственное, чего в уже выполняемых для списка пиров
запросах не было вовсе, — версия бинаря: она читается вызовом
`amneziawg-go --version` один раз за время жизни процесса на интерфейс и
кэшируется, а её отказ (например, бинаря нет в `bin_dir`) не роняет
остальную сводку — поле `version` просто остаётся пустым до следующего
рестарта.

Кроме сводки, панель умеет генерировать параметры кнопкой вместо того, чтобы
оператор придумывал их головой:

- `POST /api/ifaces/{iface}/generate/jitter` — тройка клиентского джиттера
  `Jc`/`Jmin`/`Jmax`. Кнопка стоит во вкладке «Настройки по умолчанию» и в модалке правки
  пира и **только заполняет форму** — сохранение остаётся отдельным явным
  действием, сама кнопка ничего не пишет на диск.
- `GET /api/ifaces/{iface}/generate/interface-params` — комплект
  `ListenPort`, `S1..S4`, `H1..H4`, `HeaderProtectionKey`,
  `ContentPaddingAddition`, отдельно клиентская тройка джиттера и отдельно
  клиентский сигнатурный пакет `I1` (`params.i1` в ответе), для третьей
  вкладки консоли — «Новый интерфейс». `ListenPort` — канонический порт
  выбранного профиля мимикрии (см. «Профили мимикрии I1» ниже) и печатается
  в текстовом блоке `server_block` первой строкой: оператор, поднимающий
  новый туннель, получает согласованную пару «порт + параметры» сразу и не
  должен помнить таблицу портов сам. Необязательный `?profile=quic|dns|stun`
  выбирает профиль пакета `I1` и, соответственно, `ListenPort`; без него —
  умолчание `quic`/443 (обоснование ниже). **Генератор ничего не
  применяет:** он печатает готовый текстовый блок, который оператор
  вставляет руками в `[Interface]` при подъёме нового туннеля — ни один файл
  на сервере не открывается на запись, `syncconf` не вызывается. Это
  единственная форма, в которой генерация серверных параметров совместима с
  правилом 2 репозитория («секция `[Interface]` серверного конфига
  копируется побайтово, кода, способного её изменить, в проекте не
  существует» — см. `CLAUDE.md`). `params.i1` в этом ответе — НЕ то же самое
  значение, что панель посеет в `defaults.json` этого интерфейса при его
  первом подъёме (см. следующий абзац): оба генерируются независимо, и
  третий блок вкладки существует именно затем, чтобы оператор, заводящий
  `defaults.json` руками, не перепутал одно с другим.
- `POST /api/ifaces/{iface}/generate/signature` — сигнатурный пакет `I1`
  одного из трёх профилей мимикрии (см. ниже). Необязательное тело
  `{"profile":"quic|dns|stun"}` выбирает профиль явно; без него профиль
  выводится из порта живого интерфейса, а если порт ничему не соответствует
  — маршрут отвечает 400 со списком допустимых профилей вместо того, чтобы
  выдумать один. Кнопка «Сгенерировать I1» и рядом с ней селектор профиля
  стоят у поля «Дополнительные поля» — в модалке правки пира и во вкладке
  «Настройки по умолчанию»; селектор по умолчанию подставляет профиль, выведенный из
  порта интерфейса (пусто — если порт ничему не соответствует, тогда профиль
  указывает оператор сам). Кнопка, как и кнопка джиттера, **только заполняет
  форму**: подставляет строку `I1 = ...` (заменяя прежнюю с тем же ключом,
  если была) и ничего не сохраняет.

### Профили мимикрии I1

Сигнатурный пакет `I1` — не один жёстко зашитый вид, а один из трёх
профилей, каждый имитирует структуру чужого протокола на UDP и предназначен
для своего канонического порта:

| Профиль | Что имитирует | Канонический порт |
|---|---|---|
| `quic` | клиентский Initial-пакет QUIC v1 (RFC 9000 §17.2.2), 1200 байт | `443` |
| `dns` | DNS-**запрос** (не ответ — см. ниже) | `53` |
| `stun` | Binding Request с печеньем `0x2112a442` (RFC 5389) | `3478` |

**Порт обязан соответствовать профилю.** Мимикрия без согласованного порта
не просто бесполезна — она вредна: DNS-пакет, прилетающий на udp/52441, не
прячет туннель, а выделяет его — ни один настоящий DNS-сервер там не
слушает. Поэтому:

- умолчания нового интерфейса сеются сигнатурным пакетом только когда порт
  устройства совпадает с одним из трёх канонических — иначе `I1` не сеется
  вовсе, а в журнал уходит объяснение и подсказка досеять его кнопкой из
  консоли, указав профиль вручную;
- `GET /api/ifaces/{iface}/summary` несёт поле `mimicry_mismatch` — непустую
  строку с портом, профилем и тем, что делать, когда в умолчаниях лежит
  `I1`, чей профиль (определяется по структуре самого пакета, не по
  отдельному полю — `defaults.json` мог быть заполнен руками) не
  соответствует живому порту интерфейса; консоль показывает это
  предупреждением рядом со строкой сервера, заметно и в обеих сборках
  (это чтение, а не мутация).
- Та же сводка несёт `config_warnings` — нарушения правил AWG 3.x в живом
  `[Interface]`: S1..S4 < 12 при `HeaderProtectionKey`, S4 > 32, пересечение
  H1..H4, `RandomTrailers` без `ContentPaddingAddition` (падение скорости) и при
  неравных S (тихие потери, amneziawg-go#186). Панель `[Interface]` не правит —
  это подсказка оператору (спека 2026-10-29, раздел 3).
- Ввод проверяется строже: I1..I5 — только теги `<b 0xHEX>`, `<r|rc|rd N>`
  (N 1..1000), `<t>`, вплотную; Jc ≤ 122, Jmax ≤ 1280. Выдача отказывает, если
  `Jc + I-пакеты + 1 > 128` (amneziawg-go#111).
- `GET /api/ifaces/{iface}/peers/{id}/vpnuri` — ссылка импорта AmneziaVPN
  (`vpn://`, текст), `GET …/vpnqr` — её QR. AmneziaVPN собирает туннель из
  JSON-ключей ссылки, а не из текста `.conf`, поэтому каждое поле AWG кладётся
  отдельным ключом нужного типа (порт — число, остальное — строки); в
  `client_ip` — только IPv4. В консоли — кнопки «QR для AmneziaVPN» и
  «Скопировать vpn://» в окне выдачи (спека 2026-10-29, раздел 6). Живой импорт
  на телефоне — обязательная проверка после выката. Ограничения ссылки: IPv6-адрес клиента
  в неё не попадает (пир без IPv4 получит отказ), а при пустом DNS в умолчаниях
  AmneziaVPN, вероятно, подставит свой DNS из настроек приложения, а не оставит
  системный — проверить на том же живом импорте. `ValidateDefaults` проверяет умолчания
  целиком: если в `defaults.json` осталось поле, не проходящее новые правила
  (например, Jmax > 1280 со старых времён), любая правка умолчаний будет отвергнута
  с его названием, пока это поле не исправить.

**`dns`-профиль строит DNS-запрос, а не ответ.** Прежняя версия генератора
собирала пакет с флагами DNS-ответа (`0x8580`) — структурная аномалия для
пакета, уходящего от клиента к серверу. Профиль `dns` даёт `ancount = 0` и
флаги запроса — так, как настоящий клиентский DNS-запрос выглядит на
проводе.

Умолчание профиля у `generate/interface-params` без `?profile=` — `quic`
(порт 443), а не `dns`: у совершенно нового интерфейса живого порта ещё нет,
выводить профиль неоткуда, а 443 — лучшая рекомендация из наших же (там
живёт весь QUIC-трафик, и гигабайты никого не удивляют) — ровно так собран
боевой эталон конфигурации.

**У `quic`-профиля есть оговорка, которую стоит знать до выбора порта.**
QUIC Initial — единственный из трёх профилей, чьё содержимое DPI может
расшифровать, не имея наших ключей: RFC 9001 §5.2 выводит initial-секреты
через HKDF из фиксированной публичной соли протокола и DCID клиента, а DCID
летит на проводе открытым текстом в самом заголовке — это ровно тот механизм,
которым DPI достаёт SNI из настоящего QUIC ClientHello. Применённый к нашему
пакету, тот же механизм честно расшифрует заголовок, но упрётся в AEAD-тег
поверх случайных байт полезной нагрузки — «пакет представляется QUIC Initial,
но проверка подлинности Initial проваливается» отличает нас от настоящего
QUIC дешёво и надёжно, если DPI вообще утруждается идти так далеко. `dns` и
`stun` этой уязвимости лишены: у DNS-запроса и STUN Binding Request нет
шифрования, которое можно было бы попытаться снять и не заметить подделку.
Внутри CPS это не чинится — статичные теги `<b>`/`<r>` не умеют считать AEAD
над каждый раз новыми случайными байтами полезной нагрузки, — и хуже, чем
было в приложении AmneziaVPN, это не делает: тот же самый разбор одинаково
применим к любой QUIC-мимикрии, не только к нашей. Рекомендация остаётся в
силе, потому что порт с его объёмом легитимного трафика — то, что мимикрия
вообще призвана использовать, — перевешивает этот один, глубокий и не всегда
применяемый на практике метод проверки: DPI, проверяющая AEAD у каждого
Initial-пакета на 443, платит за это заметно дороже, чем DPI, сравнивающая
байты сигнатуры.

**`H1..H4` и `I1` устроены принципиально по-разному, и это определяет, где
каждый из них уместен.** `H1..H4` — диапазонами вместо одиночных значений:
одиночное значение — это отпечаток сервера, одна и та же четырёхбайтовая
константа в каждом пакете данного типа, DPI ловит её одним сравнением,
увидев однажды; диапазон заставляет значение меняться от пакета к пакету.
Поле **двустороннее** и живёт в серверном `[Interface]` — клиент и сервер
обязаны совпадать, поэтому генератор печатает `H1..H4` только в составе
комплекта для **нового** интерфейса (`generate/interface-params`) и панель
никогда их не пишет (правило 2 репозитория). `I1`, наоборот, **односторонний**
— официальный README `amneziawg-go` прямо говорит: «Custom signature packets
does not carry any actual data, so there is no need to specify it on both
sides». Отсюда практическое следствие: `I1` можно добавить **уже
существующим** клиентам и интерфейсам, не трогая сервер и никого не
отключая, — для этого и есть отдельная кнопка и маршрут
`generate/signature`, работающие на любом интерфейсе, включая боевые `awg3`
и `awg31`. Умолчания **нового** интерфейса сеются с уже сгенерированным `I1`
автоматически при первом создании `defaults.json`; уже существующий
`defaults.json` этот сев не трогает никогда — оператор мог осознанно убрать
поле, и апгрейд панели не должен возвращать его без спроса.

**Персонализация новых подключений выполняется автоматически.** Issuer использует
настройки интерфейса как основу и формирует I1 при добавлении пира. Для STUN
выбирается SOFTWARE-вариант; transaction ID рандомизируется движком при отправке.
Число SOFTWARE-вариантов ограничено, поэтому разные пиры могут иметь одинаковое
текстовое CPS-описание. Повторный экспорт сохраняет параметры существующего пира.

Оба генератора комплекта и джиттера, а также генератор `I1`, живут в
`registerMutations` и в `readonly`-сборке недоступны (`404`) — генерация
ключей и параметров не то, что стоит давать read-only зрителю, хотя формально
она ничего не пишет.

Диапазоны, из которых генераторы выбирают значения, и жёсткие правила
протокола (`S1 + 56 ≠ S2`, попарное непересечение `H1..H4` — каждая полоса
печатается диапазоном вида `x-y`, а не одиночным значением, и т. д.) — см.
[инструкцию по установке](install.md).

## Обфускация, порт и MTU сервера

Правки серверного `[Interface]` панель не делает и в этой версии делать не
умеет — ни через веб, ни через CLI, ни как-то ещё: кода для такой записи в
бинаре нет (см. «Что делает и чего не делает», `CLAUDE.md`). Смена обфускации
(`S1..S4`, `H1..H4`, `HeaderProtectionKey`, `ContentPaddingAddition`), порта
(`ListenPort`) и MTU сервера — по-прежнему только руками, по SSH:
редактированием серверного конфига и `syncconf`/перезапуском интерфейса
напрямую. Панель об изменении узнаёт сама и ничего дополнительно настраивать
не нужно: `[Interface]` копируется из живого конфига при каждой выдаче
клиентского файла, поэтому новые конфиги подхватят правку сами.

## Миграция ключей со старой установки

До этой версии клиентский `.conf` собирался один раз при выпуске пира и лежал
файлом в `storage.client_configs` (`clients/<slug>.conf`) — приватный ключ
существовал только внутри этого файла. Теперь ключ хранится отдельно
(`storage.keys/<id>.key`, `0600`, каталог `0700`), а `.conf` собирается заново
при каждой выдаче — так правка обфускации или умолчаний не может молча сделать
уже выданные файлы негодными: файла, который мог бы устареть, больше нет.

Перенос происходит автоматически и лениво — не при каждом обращении к пиру, а
именно при попытке получить его конфиг или QR (просмотру списка пиров
приватный ключ не нужен, и миграция там не запускается): если `keys/<id>.key`
ещё нет, а `clients/<slug>.conf` есть, панель разбирает `.conf`, вычисляет
публичный ключ от найденного там `PrivateKey` и **сверяет его с публичным
ключом этого же пира в серверном конфиге**. Совпало — ключ переносится в
хранилище, а исходный `.conf` удаляется: держать один и тот же приватный ключ
в двух местах означает два места для утечки и два для расхождения. Не
совпало — перенос не выполняется, `keys/` остаётся пуст, `.conf` остаётся
нетронутым, а в журнал уходит ошибка с `id` пира и без единого ключа в
тексте: так испорченный или подменённый файл не станет тихим источником
нерабочего конфига.

Каталог `clients/` панель никогда не создаёт и никогда в него не пишет —
только читает на время миграции. По мере того как пиры получают обращение за
конфигом хотя бы один раз, каталог пустеет сам; когда в нём не осталось
файлов, его можно удалить вместе с полем `storage.client_configs` в
`config.yaml` — панель ничего не потеряет, потому что к этому моменту у
каждого пира с известным ключом он уже в `keys/`.

Пиры, для которых миграция не удалась или которые вообще заведены вручную до
установки панели (для них `storage.client_configs` ничего не даёт — файла для
переноса просто никогда не было), остаются полностью управляемыми — видны,
переименовываются, отключаются, удаляются, — но выдача конфига и QR отвечает
`404`, пока для такого пира не выполнена ротация ключей (см. «Ротация
ключей»).

## Известные ограничения

- **Пира без `PresharedKey` в серверном конфиге нельзя отключить.** Панель
  отказывает с кодом 400: сохранить в `peers.json` для обратного включения
  нечего, а вырезание блока `[Peer]` без PSK сделало бы пира невосстановимым.
  Такие пиры бывают, если заведены руками до установки панели. Удалить
  такого пира можно — отказ касается только отключения.
- **Защита от одновременной работы CLI и демона — совет, а не блокировка**
  (см. раздел CLI).
- **`awg syncconf` сбрасывает параметры устройства, которых нет в
  применяемом файле** — измерено на AmneziaWG v3.0.20260730 (`awg set awg3
  fwmark 42` → `awg syncconf awg3 <strip>` → `awg show awg3 fwmark` = `off`).
  Поэтому панель отказывается применять мутацию, если на устройстве есть
  параметр `[Interface]`, отсутствующий в файле: сверьте файл с
  `awg showconf awg3` и исправьте расхождение вручную.
- **Конфиг без пиров и без завершающего перевода строки панель обслужить не
  может** — допишите перевод строки в конец файла.

## Разработка

```bash
make test    # go test ./... и go test -tags readonly ./... — обе сборки
make vet     # go vet ./... и go vet -tags readonly ./...
```

`gofmt -l .` показывает вендоренный сторонний код (`vendor/github.com/skip2/...`,
`vendor/gopkg.in/yaml.v3/...`) — форматировать его не нужно. Свой код
проверяется адресно:

```bash
gofmt -l internal cmd
```

Пустой вывод — форматирование в порядке.
